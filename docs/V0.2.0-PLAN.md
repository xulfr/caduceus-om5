# v0.2.0 development plan (OM-5 Mark II, E148 1.1)

Status: planning. Nothing here is built or camera-tested.

## Version naming

- `v0.1.0-alphaN` stays the line for the existing feature set (alpha12 is current).
- New features go to `v0.2.0`. Until a build is ready for the owner's camera, call it
  `v0.2.0-dev` (branch work, no package hash published). The first camera package is
  `v0.2.0-alpha1`. Beta and the final `0.2.0` follow only after documented camera checks.

## Why the OM-5 II firmware "has no space"

Observation (from this repository and the Atlas):

- The update file is not loaded as one blob. The camera's own loader copies each program
  section into a fixed RAM range given by the native section descriptor table
  (`0x600284fc`, end selector `0x600463af`). Bytes outside those ranges are never loaded.
  Section 5, for example, loads `0x60843000..0x60846000`; a build that assumed `0x60847000`
  ran 3,036 bytes past the load ([startup fix](../research/OM5II-STARTUP-FIX-2026-11-06.md)).
- So the file *can* be a different size, but extra bytes do nothing unless the loader is
  told to load them. Changing the descriptor table or loader is on the boot path: a mistake
  there is the black-screen class of failure already seen four times.
- Alpha12's custom code and data live in seven small unused tails of stock sections
  (`firmware/om5ii/patch.json`): ext2 417, ext5 1,352, ext6 1,070, ext7 1,076, ext8 646,
  ext10 1,826, extvec 4 — 6,391 bytes in all. The alpha12 build audit measures what is left
  in three of them: ext6 210, ext7 52, ext10 190 bytes
  ([audit](../tests/alpha12-build-audit.json), `section_tail_space`).
- Halation, split toning or more profiles each need code, tables and UI rows. Several
  hundred bytes will not hold them.

## Ways to get room (ranked by risk, lowest first)

1. **Measure before choosing.** A complete, tool-generated map of every loaded section,
   every gap the loader actually loads, and every byte we use. Not done yet (Codex task).
2. **Runtime heap.** Allocate memory with the stock allocator after boot and keep big
   tables and state there. This project already does it: `hsl.s` takes its state block P
   (now 1,064 bytes) from E148's `malloc` once armed. Atlas: OM-3 OSD pictures must live in heap.
3. **Load from the card into heap ("load on the fly").** This already exists for data:
   looks come from one `LOOKS.BIN` on the card. The same route can carry larger tables
   and, later, code: a small resident loader reads a file, checks its hash and only then
   uses it. Costs: card access only from task context, 8.3 file names, cached heap
   buffers (Atlas E-M5 III hazard), and a defined fallback when the card or file is
   missing. OM-3 moved its films *off* the card in v0.29 so "any card works"; that is a
   usability tradeoff to decide, not a blocker.
4. **Reclaim a native feature's space.** Only with a measured need and a documented
   tradeoff (ROADMAP rule).
5. **Enlarge a loaded section** by editing the descriptor table/loader. Highest risk;
   not planned for 0.2.0.

## Feature order for 0.2.0

1. **Colour grain for Color Profiles**: implemented on this branch, emulator only
   ([note](../research/OM5II-CP-GRAIN-2026-11-18.md)). Used about 150 bytes of freed data space and
   about 20 bytes of code. Needs a camera check that grain shows in colour JPEGs.
2. **Blacks / Whites** (owner priority, 2026-11-18). Two −5..+5 rows that bend the ends of the
   brightness curve. OM-3 does this in a hook on its development stage, camera-proven there.
3. **Split toning.** Separate shadow and highlight tints on the R/G/B curves of the same stage.
4. **Clarity.** On OM-3 this is the Soft Focus pass with a weight above stock 600, so it also needs the
   Art Effect converter hook and the Soft Focus weight getter
   ([effects map](../research/OM5II-EFFECTS-MAP-2026-11-18.md)).
5. Not in 0.2.0 (owner): Glow / Frame / Star Light, halation, code loaded from the card, more slots.

Status (2026-11-19):
- **Blacks / Whites: on the tone curve page** (INFO: Hi/Sh → Black/White → Mid; −7..+7; per profile; curve
  hook), emulator-checked. The sidebar rows are gone. [Note](../research/OM5II-BLACKS-WHITES-2026-11-18.md),
  [tone page](../research/OM5II-TONE-PAGE-2026-11-19.md).
- **Split toning: three tints on the colour wheel** (Shadow / Midtone / Highlight Tint axes; any of 12 colours,
  strength 1..5; R/G/B curves), emulator-checked. [Note](../research/OM5II-SPLIT-TONE-2026-11-19.md).
- Space: removing the rows' hooks and building the 15 descriptors in the heap at arming paid for most of it; the
  FF tails of sections 3 and 9 are now used too (first use; camera check). About 30 bytes remain spread over the
  tails: any further feature needs the heap/card route below.
- **Clarity**: blocked on the Soft Focus weight. The F005 preparers `0x603937f8` (phase 0x400) and
  `0x60393342` (0x402) only set up buffers and formats (0x305 / 0x302, sizes) for the blur passes. No blend
  weight there (Ghidra decompile, 2026-11-19). The weight is set further down (`0x6038a98c` executor).
  A new row would also need a free slot in every 32-slot table (slots 0, 5, 7, 10, 11, … remain).

## Tooling (to make work cheaper and safer)

- Ghidra with the MN103 module ([nsud-dev/ghidra-mn103](https://github.com/nsud-dev/ghidra-mn103)),
  run headless and seeded with every known address (from `layout.ld`, `patch.json`, the
  Atlas reference records). Agents query named functions instead of re-disassembling.
- A space map tool and a "what touches this address" query, both writing small JSON into
  `generated/`, so agents read summaries, not dumps.
- See the Codex task in HANDOVER.md for scope.
